# 「乡野智游」答辩准备手册

> 适用：毕业设计/项目答辩。按"项目框架 → 底层逻辑 → 数据库 → 前后端设计 → 服务器 → 功能 → 解决的问题 → 预设问答"组织，可直接照读，也可当速查表。

---

## 一、项目一句话定位

**乡野智游**是一个面向县域乡村文旅的全栈系统：以 Spring Boot 3 + Vue 3 + MySQL 为基座，落地专利方案《一种面向县域文旅的 AI 多模态数字内容生成与智能导览方法及系统》的完整闭环（知识图谱 → 多模态内容量产 → 个性化路线 → 实时导览 → 智能问答 → 反馈回写），并配有 1 主 5 副的数字孪生可视化大屏。

一句话给评委：**"我们解决的不是'做一个旅游网站'，而是县域文旅'内容少、导览粗、数据看不见'三个真问题。"**

## 三、底层逻辑（核心算法）

### 3.1 专利式(1)~(4)——`GuideFormulas.java`

全部算法系数集中在 `backend/.../guide/GuideFormulas.java`，纯函数、不依赖 Spring/DB/HTTP，是唯一事实来源（single source of truth），便于单元测试与敏感性分析：

- **式(1) 景点入选分**：s = α·p + β·h − γ·c + δ·g（偏好匹配 0.40、热度 0.25、拥挤度 −0.20、内容完备度 0.15）——四项权重和为 1，拥挤度取负号体现"避堵"
- **式(2) 时间预算约束**：各景点停留时长 + 接驳步行时长 ≤ 游客计划时长，且拥挤度超阈值 τ=0.75 的景点直接不纳入路线
- **式(3) 讲解深度自适应**：由知识背景 k、互动参与 r、同行构成 q 三个因子（各 ∈[0,3]）加权后取整，输出 1简约/2标准/3深度 三档
- **式(4) EMA 热度反馈**：h^(t+1) = 0.8·h^(t) + 0.2·f^(t)——游客评价以指数滑动平均回写景点热度，越新的评价权重越高，形成"评价→热度→推荐"闭环

**关键设计决策（答辩可强调）**：游客端界面**不出现任何公式、希腊字母、权重和原始分数**——算法内核照常运行，但显示层全部翻译成人话（"非常合适""人气旺""此刻较挤""讲解内容齐全"）。公式只出现在管理端内部页面和专利文档里。这叫**"算法不动、表达人话化"**。

### 3.2 其他算法组件

- **推荐引擎**（`RecommendService`）：协同过滤 + 内容标签混合推荐，虚拟用户/虚拟评分解决冷启动
- **以图识景**（`ImageRecognitionService`）：感知哈希 pHash 比对，库中存相对路径、按站点前缀抓图计算
- **AI 服务**（`AiChatService`/`ContentGenerateService`/`VoiceGuideService`）：用户自带 Key（AES 加密存库），未配置自动降级本地模板引擎——**答辩亮点：不绑定单一厂商、不把密钥硬编码**
- **AHP-TOPSIS 乡村振兴评估**（大屏副屏）：5 维指标层 AHP 定权 + TOPSIS 贴近度排名，22 项指标墙

## 四、数据库是怎么制作的

### 4.1 设计方法

按"业务域分表、主外键约束、幂等建表"三步走，共 **24 张表**，分两个脚本：

| 脚本 | 业务域 | 表（16+8=24 张） |
|---|---|---|
| `schema.sql`（存量基础） | 用户与内容 | `user`、`category`、`tag`、`scenic_spot`、`scenic_image`、`scenic_image_hash`、`user_interest`、`rating`、`favorite`、`browse_history`、`virtual_user`、`virtual_rating`、`recommend_result`、`sys_log`、`knowledge_entry` |
| `schema-guide.sql`（方案三） | 导览闭环 | `kg_county`（县域）、`kg_entity`（图谱实体）、`kg_relation`（图谱关系）、`mm_content`（多模态内容）、`visitor_profile`（游客画像）、`guide_route` + `guide_route_item`（路线与站点）、`guide_session`（导览会话）、`guide_feedback`（评价反馈） |

### 4.2 制作与初始化流程（评委常问"数据哪来的"）

1. **建库自动**：JDBC 连接串带 `createDatabaseIfNotExist=true`，后端首次启动自动建 `rural_travel` 库
2. **建表幂等**：`spring.sql.init.mode=always` + 两个 schema 全部 `CREATE TABLE IF NOT EXISTS`，**重启不重建、不报错、可重复执行**（`continue-on-error: true` 兜底）
3. **种子数据**：`GuideDataInitializer` 首次启动时检查表是否为空，**仅空库时灌入**种子（实体、关系、内容、路线），已实测重启不会重复灌数据
4. **MySQL 本身**：`tools/mysql` 是免安装便携版，`tools/mysql-data` 是数据目录，`启动全部.bat` 按 MySQL→后端→前端顺序拉起——**换电脑拷贝整个文件夹即可运行，零环境依赖**

实测数据规模（当前库）：图谱实体 26、关系 90、多模态内容 520 条、封面 26 张。

## 五、前后端是怎么设计的

### 5.1 后端设计（Spring Boot 3）

- **经典四层**：Controller（17 个，REST 接口）→ Service（业务逻辑）→ Mapper（MyBatis-Plus）→ Entity；另有 dto/vo 出入参分离
- **包结构按业务域划分**：`guide/`（方案三导览闭环 9 个服务）、`recommend/`、`ai/`（6 个 AI 服务）、`security/`（JWT）、`config/`、`exception/`（全局异常处理）
- **统一约定**：`Result<T>` 统一返回包装、`GlobalExceptionHandler` 全局异常、`PageResult` 分页；CORS 集中配置
- **认证**：JWT 令牌，密钥与有效期走环境变量（`JWT_SECRET`），默认 12 小时
- **配置外置**：`application.yml` 所有敏感项（数据库口令、AI Key、加密密钥）均可被环境变量覆盖，默认值仅供本地开发

### 5.2 前端设计（Vue 3）

- **一个工程、三套界面**，路由懒加载：
  - **游客端**（`/`）：首页、景点列表/详情、拍照识景、图谱探索（`/guide/graph`）、路线规划（`/guide/plan`）、实时导览（`/guide/live`）、个人中心
  - **管理端**（`/admin`）：数据看板、景点/字典/用户/评分/虚拟数据/知识库/内容/日志管理 + 方案三的图谱、内容、指标三个管理页
  - **大屏**（`/bigscreen`，免登录独立路由）：1 主 5 副六屏，键盘 1-6 切换
- **状态管理**：Pinia（登录态 auth store）；路由守卫做登录鉴权与管理员鉴权
- **大屏专项设计**：固定舞台 + `transform: scale()` 等比缩放适配任意分辨率；**双源数据层**（`DATA_SOURCE='mock'|'api'` + 接口映射表，接口失败自动回落 mock）；**三态传输层**（Mock 定时器 / WebSocket / MQTT，环境变量一键切换，主题约定 `rural/{county}/flow|alert|ugc|agent`），已为后续接 Kafka/Flink 实时流预留结构

## 六、服务器用的什么

**本系统是"全内嵌便携部署"，答辩演示零外部依赖**：

| 组件 | 形态 | 端口 |
|---|---|---|
| MySQL 8.0 | `tools/mysql` 免安装便携版，数据在 `tools/mysql-data` | 3306 |
| 后端 | 内嵌 Tomcat（Spring Boot 自带），`tools/jdk17` 便携 JDK 运行 | 8090 |
| 前端 | Vite Dev Server（生产可 `vite build` 出静态文件挂任意 Nginx） | 5173 |

**如果评委问"生产环境怎么部署"**：这套便携环境只为演示与开发；生产路径是把 `vite build` 产物交给 Nginx，后端打 jar 跑在服务器 JDK 17 上，MySQL 换成正式实例——代码零改动，只改 `application.yml` 的配置项（全部支持环境变量覆盖）。

## 七、功能清单

**基础文旅**：注册登录、景点浏览/搜索/详情、收藏、评分、浏览历史、兴趣标签、个性化推荐、拍照识景（pHash）、知识库、AI 问答（自带 Key + 本地降级）

**方案三导览闭环（专利 S1-S6）**：
1. S1 知识图谱：县域实体/关系建模与可视化探索
2. S2 多模态内容量产：AI 批量生成文案/语音稿/图像/视频脚本，管理端审核
3. S3 个性化路线：式(1)(2) 打分 + 时间预算约束，输出站点序列
4. S4 实时导览：到达触发（120 米半径）、式(3) 深度三档自适应、语音讲解
5. S5 智能问答：基于县域知识库的随行问答
6. S6 反馈闭环：式(4) EMA 评价回写热度，已实测好评后热度 0.70→0.76 越过推荐阈值

**管理端**：数据分析看板、景点/字典/用户/评分/虚拟用户/知识库/AI 内容/系统日志九大管理 + 图谱/内容/政策指标三个专项页

**可视化大屏**（v2，1 主 + 5 副）：主屏 Cesium 3D 数字孪生（县域轮廓、POI 光柱、路线飞线、GPU 粒子客流、漫游/第一人称/俯视三视角、30 天时间轴回放）；副屏①知识图谱探索（G6 力导向、拖拽下钻、布局切换）②推荐算法效果（CTR/CVR/NDCG/Diversity、A/B 对比、RL 收敛）③多模态舆情（情感/平台/词云/24h/热点榜）④LLM Agent 对话（思考链流式可视化）⑤乡村振兴成效（AHP-TOPSIS 评分翻牌、22 项指标墙）。六屏跨屏联动筛选。

## 八、解决了什么问题

1. **县域文旅"内容少"**：多模态内容靠人工写不动——用 AI 批量量产 + 审核入库，520 条内容由流水线产出
2. **导览"千人一面"**：传统讲解器不分人——式(3) 按知识背景/互动/同行构成自适应三档深度
3. **路线"不合理"**：游客自己排路线要么超时要么踩挤——式(1)(2) 偏好+热度+避堵+时间预算一次约束
4. **评价"不回流"**：游客评价石沉大海——式(4) EMA 让每条评价实时影响后续推荐
5. **数据"看不见"**：县域文旅运行状况无感知——数字孪生大屏把客流、图谱、推荐、舆情、振兴成效一屏看清
6. **部署"环境难"**：答辩/演示现场装环境翻车——全内嵌便携环境，拷文件夹即运行

## 九、评委预设问答（重点背这部分）

**Q1：你的数据是真实的吗？**
分三层诚实回答：① 基础景点数据来自公开文旅资料整理入库；② 业务运行数据（评分、反馈、热度变化）是系统真实运行产生的——例如 EMA 反馈让云溪书院热度从 0.70 涨到 0.76，是真实计算结果；③ 大屏上的宏观数字（如客流 12,580、图谱 58,426 实体）是**演示口径 mock 数据**，数据层已抽离为可替换模块，接口结构按真实 API 预留，接 Kafka/Flink 实时流后只改数据源不动视图。绝不把 mock 说成真实。

**Q2：创新点在哪？**
① 式(1)-(4) 四公式构成"打分→约束→自适应→反馈"的完整数学闭环，且系数集中单点管理；② "算法不动、表达人话化"——游客端零公式、全部翻译成用户语言，兼顾专业性与可用性；③ AI 服务用户自带密钥 + 本地降级双引擎，不绑定厂商、功能不断链；④ 便携环境一键部署。

**Q3：公式为什么不展示给游客？是删掉了吗？**
没有删。算法内核（`GuideFormulas`）照常工作，每个分数都是真实计算；只是显示层做了翻译——0.78 分显示为"非常合适"，权重徽章显示为"人气旺/此刻较挤"。管理端内部页面仍保留完整公式，方便运营调参。

**Q4：数据库重启会重复灌数据吗？**
不会。建表用 `CREATE TABLE IF NOT EXISTS` 幂等执行；种子初始化器先查表计数，仅空库时灌入。已实测多次重启数据无重复。

**Q5：并发和性能怎么保证？**
MyBatis-Plus 连接池 + 无状态 JWT（天然支持水平扩展）；大屏主屏粒子流走 Cesium GPU ParticleSystem（8千/3万/10万三档可调），高频刷新用定时轮询与渲染分离，不阻塞交互。

**Q6：安全性做了哪些？**
JWT 鉴权 + 路由守卫；数据库口令、JWT 密钥、AI 加密密钥全部环境变量化，不入库不入仓；用户 AI Key 用 AES 加密存储；全局异常处理避免堆栈外泄。

**Q7：为什么用便携版 MySQL/JDK，不用 Docker？**
目标是答辩现场和普通 Windows 机器"双击即跑"；便携版免安装、免管理员权限、不污染宿主环境。Docker 是另一种可行路径，但对演示机器的虚拟化支持有要求，便携版更稳。

**Q8：图谱 5 万节点/20 万边在哪？**
专利方案的设计目标值。当前演示库实体 26/关系 90（可对账的真实数据），大屏图谱探索屏用 58,426/216,308 的演示口径展示规模化形态，G6 力导向 + 下钻按需加载的架构就是为 5 万级规模设计的——局部加载、不一次渲染全图。

**Q9：大屏和系统是一体的吗？**
是。同一个前端工程内的独立路由 `/bigscreen`（免登录），与业务前端共享构建；数据层独立成 mock/api 双源模块，后续后端就绪后切 `DATA_SOURCE='api'` 即接入真实接口。

**Q10：如果接了真实数据，哪些要改？**
只改两处：`provider.ts` 里的 `REAL_API` 端点映射 + 传输层环境变量（`VITE_WS_URL`/`VITE_MQTT_URL`）。视图组件、联动逻辑、大屏布局零改动——这是数据层抽离设计的意义。

**Q11：AHP-TOPSIS 的权重怎么来的？**
AHP 层次分析法构造判断矩阵定 5 个维度权重（产业、人才、文化、生态、组织），通过一致性检验；TOPSIS 用各乡村在 22 项指标上的取值计算与正/负理想解的贴近度，得出综合评分与排名。大屏副屏⑤的翻牌得分 86.42、排名 3/128 即此结果。

**Q12：项目还能怎么扩展？**
① 传输层切 MQTT/WebSocket 接 Kafka/Flink 实时流；② 主屏接真实倾斜摄影模型替换示意轮廓；③ 联邦学习多县数据不出域联合建模（专利方案预留）；④ 前端 `vite build` + Nginx 上生产。

## 十、答辩演示动线建议（3 分钟版）

1. **30 秒**：`启动全部.bat` 一键起三服务 → 讲"便携部署零依赖"
2. **40 秒**：游客端走一遍 图谱→规划→导览→好评反馈 → 讲"式(1)-(4) 闭环 + 人话化表达"
3. **40 秒**：管理端看数据看板 + AI 内容管理 → 讲"内容量产与审核"
4. **60 秒**：大屏 `/bigscreen` 键盘 1-6 切屏，主屏演示时间轴回放与视角切换 → 讲"数字孪生 + 跨屏联动 + 可替换数据层"
5. **10 秒**：收尾一句——"算法在后台、人话在前台、数据在大屏。"
