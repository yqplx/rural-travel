## 二、待你确认（影响具体做法，不确认就只能按默认）

1. **`AI_CRYPTO_SECRET` 沿用还是更换**（最关键）
   沿用旧值 `rural-travel-ai-crypto-2026` → 库中用户已存的 AI Key 可继续解密；换新值 → 全部失效，所有用户需重填。**默认建议沿用**，等有运维窗口再规划轮换。
2. **域名与备案**：有备案域名走 HTTPS（当前 Nginx 配置就是这套）；没有则用配置文件末尾的场景 B（IP + 80），但 `SITE_BASE_URL` 也得改成 IP。
3. **数据范围**：全量 24 表迁移，还是只迁结构与核心表（`browse_history`、`sys_log` 这两个纯行为日志表不迁可减少体积）。
4. **默认账号怎么处理**：改密、还是禁用、还是上线前从 seed 里去掉（后者需改代码，属于改动原文件，需你点头）。
5. **是否需要子路径部署**（如 `https://域名/rural/`）：当前假定根路径，若需要得给 `vite.config.js` 加 `base`，属改原文件。
6. **`sys_log` 保留天数**：当前无任何清理机制，手册里默认写 30 天，可调。
7. **服务器规格与区域**：2 核 4G 是下限，1G 堆 + MySQL + Nginx 在 2G 机器上构建前端会 OOM。

## 四、中低风险与改进建议

1. **登录无速率限制**：`/api/auth/login` 无失败计数/锁定，可被慢速暴力破解。建议 Nginx 层加 `limit_req`（如 `limit_req_zone $binary_remote_addr zone=login:10m rate=5r/m;`），但这属于改配置，需你确认是否加。
2. **token 存 `localStorage`**：前端 `store/auth.js` 把 JWT 放 localStorage，一旦有 XSS 可直接窃取。当前没有富文本渲染入口，风险可控，可后续迁移到 httpOnly Cookie。
3. **无监控系统**：目前只有 `healthcheck.sh`（cron + webhook）。够用，但没有历史指标曲线；需要的话可加 Prometheus + node_exporter。
4. **大屏首屏偏重**：2.4MB 的 `BigScreenShell` 未做拆包，弱网下首屏可能 5s+。属性能优化，不阻断。
5. **`sys_log` 无内置清理**（无 `@Scheduled`）：长期运行会持续膨胀，手册里已给 cron 清理方案。
6. **上传只校验 `Content-Type` 前缀 + 解码**：`ImageIO.read` 会真实解码，基本能挡住伪造扩展名；但未限制像素尺寸，超大分辨率图（如 20000×20000）可造成解码内存压力。10MB 体积上限已能挡住绝大多数。

## 五、回滚方案

**代码/静态资源回滚**（`deploy/scripts/rollback.sh`）：

```
releases/20261118-1600/   ← 旧版本，保留
releases/20261119-0930/   ← 新版本
app.jar -> releases/20261119-0930/app.jar
```

回滚 = 切软链回上一个 `releases/` + `systemctl restart`，**不动数据库、不动数据文件**，秒级完成。脚本会先把当前版本 tar 一份到 `backups/` 再切，切换后同样做健康检查，失败会明确报错而不是静默。

**数据回滚**：`backup-db.sh` 产出 `rural_travel-<时间戳>.sql.gz`，恢复：
```bash
sudo systemctl stop rural-travel
gunzip -c backups/rural_travel-20261118-033000.sql.gz | sudo mysql
sudo systemctl start rural-travel
```

**关键前提**：本次发布**如果包含数据库结构变更**，单独回滚 jar 是无效的（旧代码跑新表结构）——这种情况必须连数据一起回滚，且要先把变更前的备份确认可用。
